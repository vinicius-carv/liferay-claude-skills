# End-to-end run, 2026-11-22

Sample workspace created with `lfr` 3.1.0 at `C:\wt\lr-sample` (short path on purpose), Windows 11, Node 22, Liferay Portal CE 7.4 GA106 (`liferay.workspace.product=portal-7.4-ga106`). The sample is not committed.

## Setup

```
lfr create workspace lr-sample -e portal -v 7.4
cd lr-sample/modules
lfr create mvc-portlet hello-portlet
lfr create api broken-api      # bnd.bnd += Import-Package: com.example.missing,*
```

Things the scaffold did not do for us (not plugin bugs, but they bite on a fresh machine):

- `lfr` generated `gradle-wrapper.properties` with Gradle 7.3.3; with JDK 21 `initBundle` fails with `Unsupported class file major version 65`. Fixed by pointing the wrapper at Gradle 8.5.
- Both generated modules got `Bundle-SymbolicName: org.acme`; renamed to unique names.
- Workspace default product was ga132; changed to `portal-7.4-ga106` and removed the generated `liferay.workspace.bundle.url` so the cached ga106 bundle is used. `lfr init` then succeeded (about 3 min).
- GA106 does **not** start on JDK 21: the Tomcat log shows `java.lang.NoSuchFieldException: modifiers` from `com.liferay.petra.reflect.ReflectionUtil`. It starts on JDK 11 (`JAVA_HOME=C:\Program Files\Java\jdk-11`). Modules built with JDK 21 carried `Require-Capability: osgi.ee ... version=21` and stayed unresolved on the JDK 11 portal; rebuilt with JDK 11 and they resolved.

### Fixes made during the run

1. Felix Gogo's telnet server prints no prompt until the client answers its TTYPE/NAWS requests, and it sends a subnegotiation (`IAC SB TTYPE SEND IAC SE`) that the old IAC stripper mangled. `gogo()` now answers DO TTYPE / DO NAWS / SB TTYPE and strips subnegotiations properly. Test: a mock server that withholds the prompt until negotiation.
2. Real `lb -s` rows look like `3|Active|6|name (ver)|ver`; `parseLb` kept the trailing `|ver` in the name. Test added.
3. `workspaceBundles('.')` failed with a relative workspace path (the jar path was resolved against a temp cwd). Now `resolve(jar)`. Test added.
4. `test/fixtures/lb-s.txt` replaced by the real capture (19 rows, trimmed from 1616 bundles), including the broken module's `Installed` row and Resolved fragments.

## Not verified

- A skill actually being invoked by Claude through `claude -p` (auth failure above); the skill flows were followed by hand.
- Liferay DXP (license/activation screens), Maven workspaces, macOS, Linux.
- Any JDK 17 combination; GA106 on JDK 21 does not start, JDK 11 was used.
- `lfr stop` / `lfr status` on Windows: both print "not available for Windows since the Tomcat process run in another command window" and exit 0, so exit codes there say nothing. The portal was stopped by killing the Tomcat process tree; the `lfr status` / `lfr stop` rows in workspace-setup's SKILL.md are unreliable on Windows.
- SKILL.md says Liferay logs are in `bundles/tomcat*/logs/liferay.*.log`; on GA106 they are in `bundles/logs/liferay.*.log` (only `catalina.*.log` is under tomcat).
- `check-config` does not flag a disabled Gogo console, though workspace-setup's SKILL.md suggests checking whether it did.
- `source.mjs resolve` printed no `bom` field for a workspace path.
